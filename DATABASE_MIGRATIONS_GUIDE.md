## 🎯 Overview

### What are Database Migrations?

Database migrations are **version-controlled schema changes** that allow you to:
- ✅ Track database schema evolution over time
- ✅ Apply changes consistently across environments
- ✅ Rollback changes if needed
- ✅ Collaborate with team members safely

### Tools We Use

- **Alembic:** Database migration tool for SQLAlchemy
- **SQLAlchemy:** ORM for database operations
- **PostgreSQL:** Production database
- **SQLite:** Test database (in-memory)

### Migration Workflow

```
1. Modify SQLAlchemy models
2. Generate migration with Alembic
3. Review auto-generated migration
4. Test migration locally
5. Apply to staging environment
6. Verify changes
7. Deploy to production
```

```bash
# Rollback to specific revision
alembic downgrade <revision>

alembic current

# Show migration history
alembic history

# Show pending migrations

```

## 🆕 Creating Migrations

### Method 1: Auto-generate from Models (Recommended)

**1. Update your SQLAlchemy model:**

```python
# services/api-gateway/app/models/user.py
from sqlalchemy import Column, Integer, String, JSON
from app.db.base_class import Base

class User(Base):
    __tablename__ = "users"
    
    id = Column(Integer, primary_key=True)
    email = Column(String, unique=True, nullable=False)
    full_name = Column(String, nullable=False)
    
    # ✅ NEW: Add preferences column
    preferences = Column(JSON, default={})
```

**2. Generate migration:**

```bash
cd services/api-gateway

# Auto-generate migration from model changes
alembic revision --autogenerate -m "Add user preferences column"
```

**3. Review generated migration:**

```python
# alembic/versions/abc123_add_user_preferences_column.py
"""Add user preferences column

Revision ID: abc123
Revises: xyz789
Create Date: 2025-10-23 10:30:00.000000
"""
from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic
revision = 'abc123'
down_revision = 'xyz789'
branch_labels = None
depends_on = None

def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('users', sa.Column('preferences', sa.JSON(), nullable=True))
    # ### end Alembic commands ###

def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_column('users', 'preferences')
    # ### end Alembic commands ###
```

**4. Customize if needed:**

```python
def upgrade() -> None:
    # Add column
    op.add_column('users', sa.Column('preferences', sa.JSON(), nullable=True))
    
    # ✅ Set default value for existing users
    op.execute("""
        UPDATE users
        SET preferences = '{}'::json
        WHERE preferences IS NULL
    """)
    
    # ✅ Make column non-nullable after setting defaults
    op.alter_column('users', 'preferences', nullable=False)
```

### Method 2: Manual Migration

For complex changes that can't be auto-generated:

```bash
# Create empty migration file
alembic revision -m "Add custom index on user emails"
```

**Edit the migration:**

```python
def upgrade() -> None:
    # Create custom index
    op.create_index(
        'idx_users_email_lower',
        'users',
        [sa.text('LOWER(email)')],
        unique=True
    )

def downgrade() -> None:
    op.drop_index('idx_users_email_lower', 'users')
```

## ▶️ Applying Migrations

### Local Development

```bash
cd services/api-gateway

# Apply all pending migrations
alembic upgrade head

# Verify current version
alembic current

# Output:
# abc123 (head)
```

### Staging Environment

```bash
# SSH to staging server
ssh user@staging.aivolearning.com

# Navigate to project
cd /var/www/aivo-api

# Backup database first!
pg_dump -U postgres aivo_staging > backup_$(date +%Y%m%d_%H%M%S).sql

# Pull latest code
git pull origin staging

# Apply migrations
alembic upgrade head

# Restart API
systemctl restart aivo-api
```

### Production Environment

**⚠️ IMPORTANT: Always test on staging first!**

```bash
# SSH to production server
ssh user@production.aivolearning.com

# Navigate to project
cd /var/www/aivo-api

# ✅ Create database backup
pg_dump -U postgres aivo_production > backups/backup_$(date +%Y%m%d_%H%M%S).sql

# Verify backup was created
ls -lh backups/

# Pull latest code
git pull origin main

# Show pending migrations
alembic history --verbose

# Apply migrations
alembic upgrade head

# Monitor logs
tail -f /var/log/aivo-api/error.log

# Restart API
systemctl restart aivo-api

curl https://api.aivolearning.com/health
```

## ⏮️ Rolling Back Migrations

### Rollback One Migration

```bash
# Rollback the most recent migration
alembic downgrade -1

# Verify current version
alembic current
```

### Rollback to Specific Revision

```bash
# Show migration history
alembic history

# Output:
# abc123 -> xyz789 (head), Add user preferences
# xyz789 -> def456, Add homework sessions
# def456 -> ghi789, Add learners table

# Rollback to specific revision
alembic downgrade xyz789

# Verify
alembic current
# Output: xyz789
```

### Rollback All Migrations

```bash
# ⚠️ DANGEROUS: Rolls back to initial state
alembic downgrade base
```

### Emergency Rollback in Production

**If migration causes production issues:**

```bash
# 1. Immediately rollback
alembic downgrade -1

# 2. Restart API
systemctl restart aivo-api

# 3. Verify API is healthy
curl https://api.aivolearning.com/health

# 4. Investigate issue in staging
# 5. Fix migration
# 6. Re-test on staging
# 7. Re-deploy to production
```

## ✅ Migration Best Practices

### 1. Always Review Auto-Generated Migrations

```python
# ❌ BAD: Blindly trusting auto-generated migration
def upgrade() -> None:
    # Alembic might not detect all changes correctly
    op.drop_column('users', 'important_data')  # 😱 Data loss!

# ✅ GOOD: Review and add data preservation
def upgrade() -> None:
    # Preserve data before dropping column
    op.add_column('users', sa.Column('important_data_backup', sa.String()))
    op.execute("UPDATE users SET important_data_backup = important_data")
    op.drop_column('users', 'important_data')
```

### 2. Test Migrations Locally First

```bash
# Apply migration
alembic upgrade head

# Run tests to verify
pytest

# Check database schema
psql -d aivo_local -c "\d users"

# If issues found, rollback
alembic downgrade -1
```

### 3. Include Both Upgrade and Downgrade

```python
# ✅ GOOD: Both directions implemented
def upgrade() -> None:
    op.add_column('users', sa.Column('is_verified', sa.Boolean(), default=False))

def downgrade() -> None:
    op.drop_column('users', 'is_verified')

# ❌ BAD: No downgrade (can't rollback!)
def upgrade() -> None:
    op.add_column('users', sa.Column('is_verified', sa.Boolean(), default=False))

def downgrade() -> None:
    pass  # 😱 Can't rollback!
```

### 4. Handle Data Migrations Safely

```python
# ✅ GOOD: Safe data migration
def upgrade() -> None:
    # Add new column (nullable first)
    op.add_column('users', sa.Column('display_name', sa.String(), nullable=True))
    
    # Populate with default values
    op.execute("""
        UPDATE users
        SET display_name = COALESCE(full_name, email)
    """)
    
    # Now make it non-nullable
    op.alter_column('users', 'display_name', nullable=False)

def downgrade() -> None:
    op.drop_column('users', 'display_name')
```

### 5. Use Transactions

```python
# ✅ GOOD: Wrap in transaction
def upgrade() -> None:
    # All operations are wrapped in transaction by default
    # If any operation fails, entire migration rolls back
    op.create_table('new_table', ...)
    op.add_column('users', ...)
    op.create_index(...)
    
# ❌ BAD: Multiple transactions (can cause partial migration)
def upgrade() -> None:
    with op.get_context().autocommit_block():
        # Avoid this pattern unless necessary
        pass
```

### 6. Document Breaking Changes

```python
"""Add unique constraint on user emails

⚠️ BREAKING CHANGE: This migration will fail if duplicate emails exist.

Run this query first to find duplicates:
    SELECT email, COUNT(*)
    FROM users
    GROUP BY email
    HAVING COUNT(*) > 1;

Revision ID: abc123
Revises: xyz789
Create Date: 2025-10-23 10:30:00.000000
"""

def upgrade() -> None:
    # Check for duplicates
    op.execute("""
        DO $$
        BEGIN
            IF EXISTS (
                SELECT email FROM users
                GROUP BY email
                HAVING COUNT(*) > 1
            ) THEN
                RAISE EXCEPTION 'Duplicate emails found. Migration aborted.';
            END IF;
        END
        $$;
    """)
    
    # Add unique constraint
    op.create_unique_constraint('uq_users_email', 'users', ['email'])

def downgrade() -> None:
    op.drop_constraint('uq_users_email', 'users')
```

### 7. Performance Considerations

```python
# ❌ BAD: Locks table for long time
def upgrade() -> None:
    # Adding NOT NULL constraint scans entire table
    op.alter_column('users', 'email', nullable=False)

# ✅ GOOD: Add constraint without full table scan
def upgrade() -> None:
    # First, add CHECK constraint (doesn't scan table)
    op.create_check_constraint(
        'ck_users_email_not_null',
        'users',
        'email IS NOT NULL'
    )
    
    # Later migration: Convert to NOT NULL
    # (PostgreSQL 12+ can use existing CHECK constraint)
```

## 📚 Common Scenarios

### Adding a New Table

```python
def upgrade() -> None:
    op.create_table(
        'homework_sessions',
        sa.Column('id', sa.Integer(), primary_key=True),
        sa.Column('learner_id', sa.Integer(), sa.ForeignKey('learners.id'), nullable=False),
        sa.Column('subject', sa.String(), nullable=False),
        sa.Column('status', sa.String(), nullable=False),
        sa.Column('created_at', sa.DateTime(), server_default=sa.text('now()')),
        sa.Column('updated_at', sa.DateTime(), server_default=sa.text('now()'), onupdate=sa.text('now()'))
    )
    
    # Add indexes
    op.create_index('idx_homework_sessions_learner_id', 'homework_sessions', ['learner_id'])
    op.create_index('idx_homework_sessions_status', 'homework_sessions', ['status'])

def downgrade() -> None:
    op.drop_table('homework_sessions')
```

### Adding a Foreign Key

```python
def upgrade() -> None:
    # Add column
    op.add_column('homework_sessions', sa.Column('teacher_id', sa.Integer(), nullable=True))
    
    # Add foreign key constraint
    op.create_foreign_key(
        'fk_homework_sessions_teacher_id',
        'homework_sessions',
        'users',
        ['teacher_id'],
        ['id'],
        ondelete='SET NULL'
    )
    
    # Add index
    op.create_index('idx_homework_sessions_teacher_id', 'homework_sessions', ['teacher_id'])

def downgrade() -> None:
    op.drop_constraint('fk_homework_sessions_teacher_id', 'homework_sessions')
    op.drop_column('homework_sessions', 'teacher_id')
```

### Renaming a Column

```python
def upgrade() -> None:
    # Rename column
    op.alter_column('users', 'name', new_column_name='full_name')

def downgrade() -> None:
    op.alter_column('users', 'full_name', new_column_name='name')
```

### Changing Column Type

```python
def upgrade() -> None:
    # Change column type (may require USING clause)
    op.execute("""
        ALTER TABLE users
        ALTER COLUMN age TYPE INTEGER
        USING age::INTEGER
    """)

def downgrade() -> None:
    op.execute("""
        ALTER TABLE users
        ALTER COLUMN age TYPE VARCHAR
    """)
```

### Adding an Enum Type

```python
def upgrade() -> None:
    # Create enum type
    op.execute("CREATE TYPE user_role AS ENUM ('parent', 'teacher', 'admin')")
    
    # Add column with enum type
    op.add_column('users', sa.Column('role', sa.Enum('parent', 'teacher', 'admin', name='user_role'), nullable=False))

def downgrade() -> None:
    op.drop_column('users', 'role')
    op.execute("DROP TYPE user_role")
```

### Data Migration with Batching

```python
def upgrade() -> None:
    # For large tables, batch updates
    connection = op.get_bind()
    
    batch_size = 1000
    offset = 0
    
    while True:
        result = connection.execute(f"""
            UPDATE users
            SET display_name = full_name
            WHERE id IN (
                SELECT id FROM users
                WHERE display_name IS NULL
                LIMIT {batch_size} OFFSET {offset}
            )
        """)
        
        if result.rowcount == 0:
            break
        
        offset += batch_size
```

## 🔧 Troubleshooting

### Issue: "Target database is not up to date"

```bash
# Problem: Migration history is out of sync

# Solution: Check current version
alembic current

# Show all migrations
alembic history

# Stamp database to specific version (use cautiously!)
alembic stamp head
```

### Issue: Migration Fails Midway

```bash
# Problem: Migration failed, database in inconsistent state

# Solution 1: Alembic usually rolls back automatically
# Check current version
alembic current

# Solution 2: Manual rollback if needed
alembic downgrade -1

# Fix the migration code
# Re-apply
alembic upgrade head
```

### Issue: Duplicate Migration Revisions

```bash
# Problem: Two developers created migrations simultaneously

# Solution: Use Alembic's merge feature
alembic merge -m "Merge migrations" <revision1> <revision2>
```

### Issue: Can't Connect to Database

```bash
# Problem: Connection error

# Check DATABASE_URL environment variable
echo $DATABASE_URL

# Verify database is running
psql -d aivo_local -c "SELECT 1"

# Check alembic.ini configuration
cat alembic.ini
```

### Issue: Column Already Exists

```bash
# Problem: Migration trying to add existing column

# Solution: Make migration idempotent
def upgrade() -> None:
    connection = op.get_bind()
    inspector = sa.inspect(connection)
    columns = [col['name'] for col in inspector.get_columns('users')]
    
    if 'preferences' not in columns:
        op.add_column('users', sa.Column('preferences', sa.JSON()))
```

## 📊 Migration Checklist

Before applying migration to production:

- [ ] **Migration created** and reviewed
- [ ] **Upgrade AND downgrade** implemented
- [ ] **Tested locally** with real data
- [ ] **Applied to staging** environment
- [ ] **Staging tests pass** (API, integration, E2E)
- [ ] **Database backup** created
- [ ] **Rollback plan** documented
- [ ] **Team notified** of deployment
- [ ] **Monitoring** ready (logs, metrics)
- [ ] **Migration applied** to production
- [ ] **Health checks** passing
- [ ] **Rollback tested** (optional, in staging)
